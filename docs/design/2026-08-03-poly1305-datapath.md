# Poly1305 datapath rework — design

Date: 2026-08-03. **Status: implemented on 2026-08-03, in `1205c68`**
("rtl: rework Poly1305 into a 26-bit limb datapath"); measured in
`oca/hw/syn/README.md` and covered by `hw/sim/run_poly1305.py`. This
line read "approved, not yet implemented" until 2026-08-12.
Scope: `oca/hw/rtl/poly1305.sv`. Follow-up (same shape, separate work):
`oca/hw/rtl/chacha20.sv`.

## 1. Why

First ECP5 synthesis of the cores (`oca/hw/syn/README.md`) on
LFE5U-45F-6BG381C, speed grade 6, seed 1, out-of-context:

| design | TRELLIS_COMB | TRELLIS_FF | MULT18X18D | Fmax |
|--------|--------------|------------|------------|------|
| chacha20 | 3569 | 1417 | 0 | 28.66 MHz |
| poly1305 | 5001 | 885 | 65 of 72 | 22.94 MHz |
| chacha20_poly1305 | 11144 | 4777 | 65 of 72 | 26.77 MHz |

Two problems, one cause — too much arithmetic between two registers:

- **DSP-bound.** `poly1305.sv` computes `(a + n) * r` as a single
  131x128-bit multiply, which yosys maps onto 65 of the 72 multipliers
  on the device. One AEAD engine therefore consumes the chip's DSP
  budget and cannot be replicated, which is how SPEC.md expects to scale
  aggregate throughput.
- **Clock-bound.** The critical path of the AEAD engine is 37.36 ns
  (20.77 ns logic, 16.59 ns routing), entirely inside the Poly1305
  reduction stage: `prod` register -> CCU2C carry chains -> five
  cascaded MULT18X18D -> accumulator `a`. That is `reduce()` doing two
  multiply-by-5 operations, two wide adds, a compare and a conditional
  subtract in one cycle.

ChaCha20 has the mirror-image defect (two full rounds per cycle,
34.89 ns path), so fixing Poly1305 alone moves the bottleneck rather
than removing it. Both cores are in scope; Poly1305 goes first because
it is what makes the engine unreplicable.

Note on measurement noise: the AEAD engine measures faster than either
core alone. That is place & route variance. Only order-of-magnitude
changes are meaningful; single-digit percentages are not.

## 2. Goal

High clock rate and few multipliers, at a comparable cycle count.
Concretely: get the multiplier count from 65 into the ~20 range and the
critical path short enough to target >= 100 MHz, accepting roughly 8-9
cycles per 16-byte block instead of 3.

This step alone does not make the ECP5 fast. Poly1305 is inherently
serial (each block depends on the previous one). The gain here is the
freed multipliers and a removed critical path — the throughput comes
later, from the ChaCha20 rework and from replicating engines.

Order of magnitude on the LFE5U-45F, assuming both cores reach 100 MHz
(the goal, not a measurement): ~58 cycles per 64 bytes per engine with
ChaCha20 and Poly1305 running in sequence as they do today, ~36 if they
are overlapped; three engines fit (multipliers, not LUTs, being the
limit) for roughly 4 Gbps aggregate. That saturates the GbE host link
of the MVP board several times over, which is what SPEC.md now asks of
this phase; the >= 10 Gbps figure moved to the Artix-7 platform, where
DSP count and clock rate are no longer the constraint.

## 3. Arithmetic

Represent `a` and `r` as **five 26-bit digits** (5 x 26 = 130, exactly
the width of the modulus). This is the representation the reference
software implementations use, which makes a Python model a direct
comparison rather than a translation.

The reduction modulo 2^130 - 5 stops being a stage of its own. When
multiplying digit by digit, products landing above bit 130 do not need a
division to come back: since 2^130 is congruent to 5, they re-enter the
low digits multiplied by 5. The five values `5*r_j` are precomputed once
per key (a shift plus an add, no multiplier), and the reduction becomes
part of the same accumulation as the multiply. The 261-bit `reduce()`
function — today's critical path — disappears.

The work is spread **one row per cycle** — the default value of the
parallelism parameter described in section 5: on cycle *j* the five
digits of the accumulator are multiplied by digit `r_j` (or by `5*r_j`,
depending on position) and summed into five 64-bit accumulators. Five
cycles, then a normalisation pass that propagates carries between digits
and brings each back under 26 bits. At two rows per cycle the multiply
takes three cycles and roughly twice the multipliers.

Each product is 28x29 bits — small enough to cross a multiplier and its
register in a short cycle, against 130x130 today. Five products per
cycle: an estimated ~20 multipliers against 65.

Widths: on the accumulator side the multiplier does not consume a bare
digit but `a_j + n_j`, the accumulator digit plus the block digit. The
accumulator digits stay lazily reduced at about 2^26 and `n_j < 2^26`,
so that sum runs to just under 2^27 — one bit more than a digit, which
is where a bound taken on the digits alone goes wrong — while `5*r_j`
stays under 5*2^26 < 2^29. Each product is therefore below 5*2^53,
i.e. **~2^55.32: above 2^55, not below it**, and a sum of five of them
below 25*2^53 < 2^58. The product register is sized from the declared
operand widths, 28 and 29 bits, at 57; the accumulators stay 64-bit.
Both cover their sums with margin. (Replaying the digit datapath over
the official vectors and a few thousand random messages tops out at a
product of 44576944508461200 = 2^55.31, which a 55-bit bound would not
have held.)

## 4. Interface

**Unchanged.** Same ports, same `blk_ready` -> `blk` -> `last` ->
`done`/`tag` handshake, same partial-block support (`data_len` 1..16,
which the testbench exercises via RFC 8439 2.5.2 while the AEAD engine
holds it at 16). A drop-in replacement: `chacha20_poly1305.sv` is not
touched and the existing testbench stays valid as a safety net.

The handshake already carries backpressure — both the testbench and the
AEAD engine wait on `blk_ready` — so the internal latency may change
freely. The existing testbench polls `blk_ready` and `done` with a
20-cycle timeout; at ~9 cycles per block this still holds, but the
timeout is worth raising as latency margin.

Internally the FSM goes from three steps (wait / multiply / reduce) to a
sequence of short stages: one cycle to add the block into the
accumulator, five for the multiply rows, one to drain the multiplier
pipeline, one or two to normalise carries. **About 8-9 cycles per block
against 3 today**, with each cycle expected to be ~4x shorter.

**Constant time is preserved by construction**: latency does not depend
on the data. No stage iterates on the value of the accumulator, and the
final conditional subtract stays a fixed-duration combinational choice,
not a branch. This is a requirement from SPEC.md, and belongs in the
module header as a constraint rather than a remark.

## 5. Hardware targets and portability

The datapath has to run on three families: ECP5 for the MVP (18x18
multipliers, 72 on the 45F), Artix-7 200T for OCA-10 and Kintex
UltraScale+ for OCA-50, the latter two with wider DSP blocks (25x18 and
27x18, with 48-bit accumulators and integrated pre-adders) available in
much larger numbers. Exact figures for the Xilinx families are to be
confirmed against the datasheets when phase 3 starts; the design only
depends on their order of magnitude and on the multiplier shape.

Rules that follow:

- **No vendor primitives are instantiated.** The datapath stays written
  in `*` and `+`, and each toolchain infers its own multipliers — yosys
  for ECP5 today, Vivado for the real boards later. SPEC.md already
  requires this for RAM and PLL; it applies to arithmetic too.
- **Registers immediately before and after every multiply.** This is the
  shape all three families absorb into their DSP input/output registers,
  which buys frequency without a line of family-specific code.
- **Parallelism is a parameter, not a constant.** Rows processed per
  cycle stay configurable: on ECP5 pick what fits in 72 multipliers, on
  the real boards raise it to use the available silicon. Same RTL, same
  vectors, different operating point — the "same parameterized gateware"
  SPEC.md requires across OCA-10 and OCA-50.
- Digit width stays fixed at 26 bits: it divides the 130-bit modulus
  exactly, which is what turns the reduction into an addition. Making it
  parametric would require a generic reduction for no gain today.

## 6. Verification

**The new tests are written against the current core, before any RTL
changes.** Today's core is slow but correct: if the randomised testbench
passes on it, the testbench is sound. Written afterwards, a passing test
could not distinguish a correct datapath from an indulgent test.

The oracle is a Poly1305 model in Python (plain integer arithmetic). An
unvalidated model is just another implementation that can be wrong, so
**the model is first checked against the five official RFC 8439 vectors
already in `oca/tests/vectors/sources/`**; only then does it become the
reference for generated cases. No expected values are hand-typed, per
the project rule.

Generated cases target where 26-bit digits can break:

- messages of all `0xff` bytes (maximise carries between digits);
- accumulator driven close to the modulus, to exercise the final
  conditional subtract;
- partial blocks of 1 and 15 bytes;
- single-block and many-block messages;
- the degenerate `r = 0` and `s = 0` cases (already covered by RFC 8439
  A.3, kept explicit);
- a few thousand random messages of varying length.

**Non-vacuity proof**: with the tests green, deliberately break the new
RTL — remove the carry propagation between two digits — and confirm the
tests fail, and fail for the right reason. A test that passes against
broken RTL is decoration.

Regression checks: the three AEAD tests unchanged, `verilator -Wall`
clean, and a before/after synthesis run recording multiplier count and
critical path.

## 7. Follow-up, not part of this work

- `chacha20.sv`: one round per cycle instead of two (20 cycles instead
  of 10, half the combinational path), same parameterised approach.
- Overlapping ChaCha20 and Poly1305 inside the AEAD engine, which today
  runs them strictly in sequence.
- Parallel Poly1305 over precomputed `r^k` powers — the standard way to
  break the serial dependency, a much larger design, deliberately out of
  scope.
